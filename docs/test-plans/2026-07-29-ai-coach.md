# AI Coach — Human Test Plan

Generated from the implementation at `dd1a3d6` against
`docs/implementation-plans/2026-07-29-ai-coach/test-requirements.md`.
Automated coverage: PASS — all 24 acceptance criteria resolve to verified
coverage (156 tests across six suites; `npx tsc --noEmit` clean).

## Prerequisites

- Dev client build on simulator or device: `npm run ios` (WatermelonDB is native — Expo Go will not work)
- A real Anthropic API key, and a second deliberately-wrong string for the 401 walk
- **At least two pre-existing routines** with known contents (import from the bridge, or use existing). Before starting, write down the exact routine count and the name + exercise list of one of them — call it `CONTROL`. Several checks below depend on it.
- Green baseline: the six suites passing individually, `npx tsc --noEmit` exiting 0

## Walk 3: Create flow end-to-end + data safety (AC2.1 rendering, AC3.1 card, AC3.2 navigation)

| Step | Action | Expected |
|---|---|---|
| 3.1 | Confirm your `CONTROL` notes from Prerequisites are written down | Routine count and `CONTROL` contents recorded |
| 3.2 | Routines tab → "AI Coach" | Header reads "AI Coach" (not "Edit with AI Coach") |
| 3.3 | Send `Build me a 3-exercise push day with a superset` | Your text appears right-aligned; "Coach is thinking…" with a spinner appears while in flight; Send and the input are disabled |
| 3.4 | Wait for the reply | Reply renders as a left-aligned assistant bubble. The prose should reference your goals/equipment from Walk 1 — evidence the context reached the model |
| 3.5 | Inspect the draft card | Routine name, notes if any, one row per exercise with a kind tag (`strength`/`cardio`/`stretch`), sets×reps or `m:ss` duration, `Nw` warmups, `Rest: Ns`. Superset members sit under an italic "Superset: \<label\>" heading and are indented |
| 3.6 | **Before tapping Accept**, go Back and open the Routines tab | Routine list is unchanged — no new routine, `CONTROL` untouched. This is the inertness invariant on real data |
| 3.7 | Return to AI Coach (note: the conversation resets — see Walk 6), regenerate a draft, then tap "Accept" | Button shows "Accepting..." briefly, then navigation lands on `/routine/<id>` |
| 3.8 | Inspect the new routine detail | Every drafted exercise present, in draft order, with the drafted targets and rest |
| 3.9 | **Data-safety check:** back to Routines tab | Routine count is exactly your recorded count **+1**. Open `CONTROL` — its name and full exercise list are identical to your notes. A create-mode accept must never overwrite an existing routine |

## Walk 7: Error and retry flows (AC4.2, AC4.3, AC4.4, AC4.5 no-crash halves)

| Step | Action | Expected |
|---|---|---|
| 7.1 | **Airplane mode.** Enable it, open AI Coach, send `Build me a leg day` | Inline error bubble above the input bar: "Couldn't reach the AI service. Check your connection." with a "Retry" control. Your user message remains in the transcript. No crash |
| 7.2 | Disable airplane mode, tap "Retry" | The same turn completes — a reply appears. The transcript holds exactly **one** copy of your user message, not two |
| 7.3 | **Wrong key.** Settings → replace the key with `sk-ant-invalid-000` → Save → AI Coach → send anything | Error bubble: "API key rejected — check Settings", plus an "Open Settings" link **and** a Retry control. No crash |
| 7.4 | Tap "Open Settings", restore the real key, Save, return and Retry | Turn completes normally |
| 7.5 | *Opportunistic:* if any non-401 HTTP failure occurs during these walks (e.g. 429/500/529) | Bubble reads "The AI service returned an error (\<status\>). Try again." and the app stays usable |
| 7.6 | *Opportunistic:* if an unreadable response occurs | Bubble reads "Got an unreadable response. Try again." and the app does not crash |
| 7.7 | Trigger any error, then tap Retry and watch closely | While retrying, the stale error clears and the typing indicator shows — the bubble does not linger next to a spinner |

| AC3.1 *(card)* | Card layout and superset grouping are rendering logic | Walk 3.5–3.6 |
| AC3.2 *(navigation)* | `router.push` needs an expo-router runtime | Walk 3.7 |
| AC3.6 *(single card)* | "Only the latest is Accept-able" is enforced by rendering one card bound to `pendingDraft` | Walk 4.3 |
| AC4.1 *(screen state)* | Missing-key screen and Settings link are screen code | Walk 2.2–2.3 |
| AC4.2 *(copy)* | `error.kind` → copy mapping is rendering | Walk 7.3 |
| AC4.3 *(bubble + retry UX)* | Bubble and Retry `Pressable` are screen elements | Walk 7.1–7.2 |
| AC4.4 *(bubble, no crash)* | Reproducing a specific non-401 status against the live API is opportunistic | Walk 7.5 |
| AC4.5 *(no crash)* | Malformed bodies cannot be induced reliably against the live API | Walk 7.6 |
| AC5.1 *(mount reset)* | Reset firing from the screen's render path needs a React lifecycle | Walk 6 |
