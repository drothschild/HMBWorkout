# Apple Watch Companion Design

## Summary

This design adds a watchOS companion app to HMBWorkout so a workout can be run entirely
from the wrist while the phone stays in a bag. Because React Native doesn't run on
watchOS, the watch app is a separate, hand-written Swift/SwiftUI codebase that talks to
the existing Expo/React Native iOS app over WatchConnectivity — declared as an Expo
config plugin so its native target is regenerated by `expo prebuild --clean` rather than
hand-maintained under `ios/`.

The central design move is keeping the watch decision-free. Instead of porting the
Rill session-flow rules to Swift, the phone runs the existing engine once as a silent
dry run to project the entire ordered sequence of workout stops a routine will produce,
and ships that flat schedule to the watch as a single `SessionPlan`. The watch only
walks and displays that list; it never decides what comes next. As the user logs or
skips sets, the watch queues each capture locally and relays it to the phone over two
redundant channels — a fast bidirectional mirroring session for live delivery, and a
slower but guaranteed store-and-forward queue that survives an unreachable or
force-quit phone. When captures arrive, the phone replays them through the real engine
dispatch, in order and deduplicated by a client-generated id, so a watch-logged set
becomes an ordinary engine-decided, WatermelonDB-persisted, vault-synced set with no
watch-specific logic in the decision path. The watch separately runs its own
`HKWorkoutSession` to get live heart rate and calories and to own the resulting
`HKWorkout`, with the phone's existing HealthKit export suppressed for watch-run
sessions so the two devices never save a duplicate workout.

## Definition of Done

**Deliverable:** A watchOS companion target in the HMBWorkout repo, declared via an Expo
config plugin so it survives `expo prebuild --clean`, written in Swift/SwiftUI, paired to
the existing iOS app over WatchConnectivity + App Groups.

**Success looks like:** The user starts a routine on the phone, puts the phone in a bag,
and completes the entire workout from the wrist — seeing the current exercise, set
position, target reps/weight, and a live rest countdown; entering actual reps, weight, and
RPE per set (with Double Tap as a no-touch "set done"); and watching live heart rate and
active calories throughout. The watch runs an `HKWorkoutSession`, so it closes Activity
rings and saves an `HKWorkout` with real per-sample HR data. The user can also check what
they lifted last time for the current exercise, and glance at recent workouts. Every set
logged replays through the phone's Rill engine on reconnect — the `.lv` rules remain the
only thing that decides advancement — and the session lands in WatermelonDB and syncs to
the vault exactly as a phone-logged one does.

**Explicitly out of scope:** routine authoring/editing on the watch, the AI coach on the
watch, Android/Wear OS, EAS/TestFlight pipeline work, and any watch-side re-implementation
of session-flow logic. Heart rate and calorie data land in Apple Health only — they are
**not** written into the vault markdown, so `src/interop/format.ts` and its
`../workout-bridge/src/contract.ts` mirror are untouched by this design.

### Confirmed decisions

| Decision | Choice |
| --- | --- |
| Session-flow authority | **Capture + replay** — phone dry-runs the engine into a flat set schedule; watch captures intents and decides nothing |
| Watch scope | **Session + history** |
| HealthKit ownership | **Watch owns the `HKWorkout`**; phone's existing `saveWorkout` stays as the phone-only fallback |
| Distribution | Paid developer account, **local Xcode builds** to real hardware |
| Hardware target | **Series 9 / Ultra 2 or newer** — watchOS 10+, Double Tap available |

## Acceptance Criteria

### watchos-companion.AC1: A full workout runs from the wrist
- **watchos-companion.AC1.1 Success:** Current exercise title, phase (warmup/working), and
  "Set N of M" render from the received schedule
- **watchos-companion.AC1.2 Success:** Reps, weight, and RPE are each enterable via Digital
  Crown and are captured with the set
- **watchos-companion.AC1.3 Success:** Completing a set advances to the next stop with no
  phone involvement
- **watchos-companion.AC1.4 Success:** A rest countdown runs for the stop's `restSeconds`
  and expires with a haptic
- **watchos-companion.AC1.5 Success:** A set can be skipped; it is captured as
  `kind: .skipped` and advances identically to a logged set
- **watchos-companion.AC1.6 Success:** A superset group alternates between members in the
  same order the engine would have chosen
- **watchos-companion.AC1.7 Success:** Double Tap logs the current set without touching the
  screen

### watchos-companion.AC2: The projection matches the engine, and replay reproduces it
- **watchos-companion.AC2.1 Success:** For any routine, the projected stop sequence equals
  an actual engine walk, step for step
- **watchos-companion.AC2.2 Success:** A superset group with mismatched per-member set
  counts projects the same round-robin order the engine produces
- **watchos-companion.AC2.3 Edge:** A zero-set entry is skipped past in the projection and
  never appears as a stop (engine convention 10)
- **watchos-companion.AC2.4 Edge:** A duration-only entry projects with
  `targetDurationSeconds` and no `targetReps`
- **watchos-companion.AC2.5 Failure:** A routine whose every entry totals zero sets produces
  no schedule and is refused, matching `startSessionFromRoutine`'s existing rejection
- **watchos-companion.AC2.6 Success:** Replaying captures in ordinal order produces
  `session_sets` rows identical to logging the same values on the phone
- **watchos-companion.AC2.7 Success:** The same `clientId` delivered over both channels
  produces exactly one logged set
- **watchos-companion.AC2.8 Failure:** A capture whose dispatch returns `Err` halts replay
  at that capture — earlier captures stay applied, later ones reach review unapplied
- **watchos-companion.AC2.9 Failure:** A capture carrying a stale `scheduleId` is never
  applied and appears in the review payload

### watchos-companion.AC3: Both transport channels deliver
- **watchos-companion.AC3.1 Success:** A `SessionPlan` sent via `updateApplicationContext`
  arrives on the watch
- **watchos-companion.AC3.2 Success:** A `CapturedSet` sent via
  `sendToRemoteWorkoutSession` arrives in JS with the iOS app backgrounded and screen off
- **watchos-companion.AC3.3 Success:** A `CapturedSet` sent via `transferUserInfo` arrives
  after the phone has been out of range and returned
- **watchos-companion.AC3.4 Failure:** With mirroring unavailable (force-quit phone),
  captures still arrive via `transferUserInfo` once the app next runs

### watchos-companion.AC4: Live metrics
- **watchos-companion.AC4.1 Success:** Heart rate updates on the watch during an active
  session
- **watchos-companion.AC4.2 Success:** Active energy accumulates and is displayed
- **watchos-companion.AC4.3 Failure:** A HealthKit authorization denial or error is logged
  and swallowed — the session continues and set capture is unaffected

### watchos-companion.AC5: Captures are durable
- **watchos-companion.AC5.1 Success:** A captured set persists across a watch app
  termination and relaunch
- **watchos-companion.AC5.2 Success:** A capture leaves the queue only after delivery is
  confirmed
- **watchos-companion.AC5.3 Success:** A session run entirely with the phone powered off
  syncs completely once the phone returns
- **watchos-companion.AC5.4 Edge:** A full multi-exercise routine's captures stay within
  `transferUserInfo`'s 64KB per-message limit, chunking if needed
- **watchos-companion.AC5.5 Failure:** A delivery failure leaves the capture queued for
  retry rather than dropping it

### watchos-companion.AC6: History on the wrist
- **watchos-companion.AC6.1 Success:** `historyMirror` builds recent working sets per
  exercise from `getExerciseWorkingSetHistory`, warmups excluded
- **watchos-companion.AC6.2 Edge:** An exercise with no prior history produces an empty
  list, not a missing key
- **watchos-companion.AC6.3 Success:** The active set view shows the most recent working
  sets for the current exercise
- **watchos-companion.AC6.4 Success:** Recent workouts are browsable on the watch
- **watchos-companion.AC6.5 Success:** Both render with the phone unreachable

### watchos-companion.AC7: Exactly one HKWorkout
- **watchos-companion.AC7.1 Success:** A watch-run session saves one `HKWorkout` from the
  watch with per-sample heart rate attached
- **watchos-companion.AC7.2 Success:** The phone's `saveWorkout` is suppressed when
  `health_export_owner` is `'watch'`
- **watchos-companion.AC7.3 Success:** A phone-only session still exports via the existing
  path, with `health_export_owner` `'phone'`
- **watchos-companion.AC7.4 Edge:** The v3 → v4 migration leaves existing sessions readable,
  defaulting to `'phone'`

### watchos-companion.AC8: Cross-cutting behaviors
- **watchos-companion.AC8.1:** The `.lv` rules remain the only code that decides
  advancement — no phase or advancement branching exists in Swift or in `src/watch/`
- **watchos-companion.AC8.2:** `src/interop/format.ts` and its
  `../workout-bridge/src/contract.ts` mirror are unchanged by this work

## Glossary

- **Rill / `.lv`**: A custom pure functional language used only for HMBWorkout's
  session-flow logic. Files with the `.lv` extension (e.g. `transition.lv`) implement
  `transition(state, event) → Result({state, effects})`, the single function that
  decides all phase advancement.
- **FCIS (Functional Core / Imperative Shell)**: The app's core architectural
  invariant — all session-flow decisions live in the pure Rill engine (the "core");
  everything else (UI, native modules, persistence) only shapes payloads and runs
  side effects (the "shell").
- **Engine convention N**: Shorthand, used throughout this repo's `AGENTS.md`, for one
  of a numbered list of non-obvious rules governing how the Rill engine behaves (e.g.
  convention 9 = superset round-robin logic, convention 10 = zero-set entries are
  skipped past, never landed on). Cited here to justify why the watch's schedule
  projection stays valid.
- **WatermelonDB**: The on-device database (SQLite on iOS) that stores routines,
  sessions, and sets — the local source of truth prior to and independent of vault
  sync.
- **The vault**: The Obsidian vault that workout logs sync to as markdown, via a
  Mac-side HTTP bridge (`workout-bridge`) — the durable record that lives outside the
  phone.
- **Expo config plugin**: A script that customizes the native iOS/watchOS project
  generated by `expo prebuild`, so a native change (a new target, an entitlement)
  survives being regenerated rather than requiring a hand-edit under `ios/`.
- **`expo prebuild --clean`**: Regenerates the native project from `app.json` and its
  config plugins, discarding anything not produced by a plugin. Native customization
  must go through a plugin to survive it.
- **HealthKit**: Apple's framework for health and fitness data. HMBWorkout currently
  only writes to it; this design adds read access for live heart rate.
- **`HKWorkoutSession`**: The HealthKit API representing an in-progress workout on
  watchOS. Running one is required to close Activity rings, keep the app alive in the
  background, and receive live sensor data.
- **`HKLiveWorkoutBuilder`**: The companion API that accumulates live samples (heart
  rate, active energy) during an `HKWorkoutSession` and finalizes them into a saved
  workout.
- **`HKWorkout`**: The finished, saved HealthKit record of a completed workout,
  including per-sample heart rate. This design ensures exactly one is created per
  session.
- **Activity rings**: Apple's daily move/exercise/stand goal visualization on the
  watch face; only credited while a real `HKWorkoutSession` is running.
- **WatchConnectivity / `WCSession`**: Apple's framework for phone-watch
  communication. This design uses three of its distinct transport primitives
  differently:
  - **`updateApplicationContext`**: sends the latest state (here, `SessionPlan`); a
    new value replaces rather than queues prior ones — used for the schedule, since
    only the current one ever matters.
  - **`transferUserInfo`**: a FIFO, guaranteed-delivery queue (64KB per message) that
    survives app kills and out-of-range gaps — the durable channel for captured sets.
  - **Mirroring (`startMirroringToCompanionDevice()` / `sendToRemoteWorkoutSession`)**:
    a newer (iOS 17+/watchOS 10+), bidirectional channel tied to an active
    `HKWorkoutSession` that keeps the phone app alive in the background — the fast,
    best-effort channel.
- **App Group**: An Apple entitlement letting the iOS app and the watch target share a
  sandboxed data container, used here so both targets can be built and installed under
  one shared identity.
- **Double Tap**: A watchOS 10+ gesture (tapping thumb and index finger together) that
  triggers the primary on-screen action without touching the display — used here as a
  no-touch "log this set" while holding weights.
- **Digital Crown**: The physical scroll wheel on Apple Watch, used here for numeric
  entry (reps, weight, RPE) without a tap-driven keyboard.
- **RPE (Rate of Perceived Exertion)**: A lifter's subjective rating of how hard a set
  felt, one of the three values captured per set alongside reps and weight.
- **Superset**: A routine structure where two or more exercises alternate rounds
  back-to-back with no rest between members; the engine round-robins through the
  group.
- **`clientId`**: A UUID minted per captured set at capture time, used purely as an
  idempotency key. Because a set can arrive over both transport channels, replay
  treats a repeated `clientId` as the same set rather than logging it twice.
- **`scheduleId`**: A UUID identifying one projected schedule (`SessionPlan`). Only a
  phone-side `ReplaceExercise` mints a new one; a capture carrying a stale
  `scheduleId` is treated as orphaned rather than applied.
- **`ordinal`**: The position of a stop within the projected schedule, used as the
  join key between a `CapturedSet` and the stop it belongs to during replay.
- **Sentinel value**: A placeholder (e.g. `-1` standing in for a missing RPE) used
  instead of `null`/`undefined` at a boundary that can't represent absence natively —
  an existing Rill-engine convention. Noted here only to say the watch wire contract
  deliberately avoids it, using genuinely optional fields instead.
- **Golden fixtures**: Shared JSON test fixtures, checked into the repo, that both the
  TypeScript and Swift test suites run against — letting the two independently
  declared halves of the wire contract be verified against the same known-good data.
- **Property-based testing**: A testing technique that generates many randomized
  inputs (here, randomly generated routines) and asserts an invariant holds for all of
  them, rather than hand-writing individual example cases — used to check the
  projected schedule always matches an actual engine walk.
- **`workout-bridge`**: The separate Mac-side repo/HTTP service that reads and writes
  the Obsidian vault's `_sync/` folder over Tailscale; the phone app syncs sessions to
  markdown through it.
- **`@bacons/apple-targets`**: A third-party Expo config-plugin library that generates
  additional native targets (such as a watchOS app) from Expo config — used here to
  scaffold the watch target so it survives `expo prebuild`.
- **Zustand**: A lightweight React state-management library. It backs the app's
  "imperative shell" store, which holds the active session and dispatches events into
  the Rill engine.

## Architecture

React Native does not run on watchOS, so the watch app is hand-written Swift/SwiftUI — a
second codebase in a second language, invisible to `npm test`. Everything below follows
from that and from one decision: **the watch decides nothing.**

### The schedule projection

`advance_after_set` in `src/engine/rules/transition.lv` depends only on `entries`,
`setIndex`, `exerciseIndex`, and `supersetPosition` — never on the *values* logged (engine
convention 9). The full ordered sequence of stops through a routine is therefore a pure
function of that routine.

`src/watch/schedule.ts` exploits this: it walks `transition` with no-op executors from
`StartSession` to completion and records every stop. The watch renders a projection the
engine itself produced. The FCIS invariant survives intact — the `.lv` rules remain the
only thing that decides advancement; they just decide it up front instead of one set at a
time.

Two consequences worth stating. "Skip Set" on the watch is free, because `SetDone` and
`LogSet` advance identically, so skipping stays on-schedule. And `ReplaceExercise` is the
only event that can invalidate a schedule — it is phone-only, and it mints a new
`scheduleId`.

### Dual-channel transport

The watch runs an `HKWorkoutSession` regardless of transport: it is the only way to get
heart rate, active energy, and background execution on watchOS. Two channels ride on top:

- **Fast path** — `HKWorkoutSession.startMirroringToCompanionDevice()` (iOS 17+/watchOS
  10+). The system launches the iOS app in the background and keeps it alive for the
  duration of the session, giving a bidirectional `sendToRemoteWorkoutSession(data:)`
  channel with no reachability requirement. Used for live HR/calorie streaming and prompt
  capture delivery.
- **Durable path** — `WCSession.transferUserInfo(_:)`. FIFO, guaranteed, queues across app
  kills and out-of-range gaps. 64KB per message. This is the correctness backbone; the
  fast path is an optimization on top of it.

The fast path can fail in ways the durable path cannot: a user-initiated force-quit of the
iOS app kills mirroring permanently for that session. Because every capture also rides the
durable queue, that degrades to "sync happens later" rather than "data is lost."

**Every capture can therefore arrive twice.** `clientId` is the idempotency key and
deduplication on replay is mandatory, not defensive.

### Data flow

```
SESSION START (phone)
  routine → schedule.ts dry-run → SessionPlan{scheduleId, stops[], history[]}
         → updateApplicationContext (262KB ceiling) → watch

DURING (watch, phone may be asleep/away)
  HKWorkoutSession + HKLiveWorkoutBuilder → live HR + kcal
  user logs set → SetCaptureQueue (local, durable)
                → sendToRemoteWorkoutSession   (fast, best-effort)
                → transferUserInfo             (durable, guaranteed)

ON DELIVERY (phone)
  replay.ts: sort by ordinal → drop seen clientIds → dispatch LogSet/SetDone
           → engine decides → PersistSet → WatermelonDB → existing vault sync

SESSION END (watch)
  builder.finishWorkout() saves the HKWorkout; phone suppresses its own export
```

### Wire contract

Both payloads are declared twice — once in Swift, once in TypeScript. This is the same
hazard class as the markdown contract copied into `../workout-bridge/src/contract.ts` and
the AI turn shape declared in three places (`AI_TURN_SCHEMA`, the validators, the persona
prose). It is mitigated the same way the repo already mitigates those: by pinning it in
tests on both sides, against shared golden fixtures.

```swift
struct SessionPlan: Codable {
  let scheduleId: String          // UUID; any ReplaceExercise mints a new one
  let sessionId: String
  let routineName: String
  let stops: [Stop]
  let history: [ExerciseHistory]
}

struct Stop: Codable {
  let ordinal: Int                // join key for replay
  let exerciseId: String
  let exerciseTitle: String
  let phase: Phase                // .warmup | .working
  let setNumber: Int
  let totalSets: Int
  let targetReps: Int?
  let targetDurationSeconds: Int?
  let restSeconds: Int
  let supersetGroup: String?
}

struct ExerciseHistory: Codable {
  let exerciseId: String
  let recentWorkingSets: [HistorySet]   // reps + weightKg + loggedAtMs
}

struct CapturedSet: Codable {
  let clientId: String            // UUID — idempotency key, required
  let scheduleId: String
  let ordinal: Int
  let kind: Kind                  // .logged | .skipped
  let reps: Int?
  let weightKg: Double?           // KG, matching session_sets and HealthKit
  let rpe: Double?
  let durationSeconds: Int?
  let capturedAtMs: Int64
}
```

Weight is KG on the wire, matching `session_sets.weight_kg` and HealthKit. Optional fields
are genuinely absent, not sentinelized — the sentinel convention (engine convention 8) is
an engine-boundary concern and must not leak onto the wire.

### Replay and divergence

Replay dispatches through the store's real `dispatch`, so `PersistSet` fires and the
session reaches WatermelonDB and the vault by the existing path with nothing
special-cased.

**On the first `Err`, replay halts — it does not skip.** Rejections are never silent in
this codebase (engine convention 5), and `serializeSession`'s contract is explicit that
silently skipping a set *is* the data-loss bug. Unapplied captures go to a review screen
offering discard-or-force.

Divergence is narrow by construction. The only real sources are:

- The user also logged on the phone, consuming an ordinal the watch later claims.
- A phone-side `ReplaceExercise` invalidated the schedule; captures carrying the stale
  `scheduleId` are orphaned into review.

### HealthKit ownership

The watch runs `HKWorkoutSession(.traditionalStrengthTraining, .indoor)` with
`HKLiveWorkoutBuilder`, requests read authorization for `heartRate` and
`activeEnergyBurned`, and saves via `finishWorkout()`.

The phone must then not write its own. Two `HKWorkout` records over the same window do not
merge — the Health app shows both and resolves by source priority. A
`health_export_owner` column on `sessions` (`'watch' | 'phone'`) gates
`onCompleteSession`'s existing export call. That is a WatermelonDB schema v3 → v4 change
with a real migration on a table holding live data.

This is a genuine change to the `src/health` contract, which is documented as write-only
(`AGENTS.md`). Read authorization is now required. The "all HealthKit errors are logged and
swallowed" invariant is unchanged and extends to the watch: a Health failure must never
affect capture, replay, DB, or sync state.

## Existing Patterns

This design follows several established patterns rather than inventing new ones:

- **FCIS (`AGENTS.md`, "Architecture").** `src/watch/` is split the same way the rest of
  the app is: `schedule.ts`, `envelope.ts`, `replay.ts`, and `reconcile.ts` are pure and
  jest-covered; the native module and the Swift app are shell. No session-flow decision
  moves out of `src/engine/rules/*.lv`.
- **Offline-first queue with a reachability gate (`src/sync`).** `SetCaptureQueue` mirrors
  `syncService.ts`: write locally first, flip status only after confirmed delivery, treat
  an unreachable counterpart as a no-op rather than an error, and keep network-vs-protocol
  failures as distinct types.
- **Injected dependencies for testability (`HealthKitSaveDeps`, `AiChatDeps`).**
  `replay.ts` and `reconcile.ts` take their store and repository structurally so they test
  in the node jest project, exactly as `sessionRehydrate.ts` takes the store structurally
  rather than importing the global one.
- **Contract-mirroring discipline.** The two-language envelope is treated as the known
  hazard it is, following the precedent set by the markdown contract and the AI turn shape.
- **Config-plugin-only native customization (`AGENTS.md`, "Native iOS project").** Every
  native change — the watch target, App Group, entitlements, background modes — lands in
  `app.json` or `plugins/`. Nothing is hand-edited under `ios/`.

Divergence: `src/health` becomes read+write rather than write-only, justified by live
metrics being impossible otherwise. The swallow-all-errors invariant is preserved.

New territory with no existing pattern: Swift source, watchOS UI, and XCTest. There is no
Swift test infrastructure in the repo today.

## Additional Considerations

**The simulator is nearly useless for this project.** No heart rate, no real mirroring, and
paired-simulator WatchConnectivity is unreliable. Almost all verification is on real
hardware, which makes iteration slow and makes the pure-TS Phase 3 disproportionately
valuable — it is the only part with fast, trustworthy feedback.

**Test coverage is structurally thin.** `npm test` runs a single node project. Swift gets
XCTest only, `src/app` and `src/components` already get nothing (`AGENTS.md`, "Testing
gotchas": PR #66 shipped a collapsed ScrollView past 159 passing tests). A green run proves
even less than usual here. The property-based schedule test is the highest-value artifact
in the project precisely because supersets and zero-set entries are where this codebase's
real bugs have historically lived (PRs #74, #76, #78).

**Third-party watch apps cannot use always-on display.** Only Apple's own Workout app gets
ambient mode. The screen dims roughly five seconds after wrist-down even mid-session. Rest
timers and metrics must be designed for glance-on-raise, not continuous visibility.

**Force-quit is unrecoverable for mirroring.** If the user swipes away the iOS app, that
session's mirrored channel never resumes. The durable queue is what makes this survivable,
which is why it is the backbone rather than the fallback.

**Effort estimate — solo:** 31–48 focused engineering days across the eight phases. Against
this repo's demonstrated cadence — TDD, one PR per task, one to four adversarial review
cycles each — roughly 8–12 weeks part-time. Two risks dominate: a negative Phase 1
mirroring result costs live phone state (a scope loss, not a schedule loss), and an
`@bacons/apple-targets` incompatibility adds 5–8 days for a hand-rolled config plugin.

**Effort estimate — agent-assisted:** roughly **18–29 days of engaged time, 4–7 weeks
calendar**. Agent assistance compresses this project unevenly, because the phases differ in
whether they have a fast feedback loop:

| Phase | Solo | Agent-assisted | Constraint |
| --- | --- | --- | --- |
| 1 Spikes | 2–4 | 1–2 | Answer-gated, not code-gated |
| 2 Scaffolding | 3–5 | 2–4 | `xcodebuild` errors iterate well; Developer portal and Xcode GUI do not |
| 3 TS core | 3–4 | 0.5–1 | Pure, jest-covered, property-based — largest speedup |
| 4 Link module | 4–6 | 2–3 | Half TS, half device-gated |
| 5 Watch core + UI | 8–12 | 5–8 | Capped by build/install/wear cycles |
| 6 Replay + HK + migration | 5–8 | 2–3 | Mostly testable TS |
| 7 History | 2–3 | 1–1.5 | Small |
| 8 Field testing | 4–6 | 4–6 | No speedup available |
| | 31–48 | **18–29** | |

Two effects hold the gain to roughly 2x rather than an order of magnitude. Swift written
without test coverage pushes more defects into manual verification than careful hand-written
code would, returning some of the writing-time saving as extra device cycles. And **Phase 8
is calendar-bound by workout frequency** — six to ten real gym sessions at four lifts a week
is two-plus weeks that no amount of parallelism touches. That floor, not the code, sets the
finish date.

Parallel agents help Phases 3, 6, and 7 and barely help 2, 5, and 8: there is one Apple
Watch and one tester, and concurrent `xcodebuild` runs contend for DerivedData regardless.
Worktree isolation is also expensive here — `ios/` is gitignored and regenerated per
checkout, and Metro needs a local `node_modules` where jest does not — so native work should
be serialized in the main checkout and worktree parallelism reserved for the pure-TS phases.

**Highest-leverage mitigation: a watch-side state-injection harness, built early in Phase 5.**
A debug screen that loads a synthetic `SessionPlan` and synthetic heart rate, letting every
UI state be exercised without running a workout. This is an established pattern in this repo
— PRs #74 and #77 were both verified by injecting engine state to reach the session screen
in zero taps — and it converts most of Phase 5's verification cycles from
workout-shaped to seconds-long.

**Unmeasured multiplier:** watch build-and-install time on the development machine. It is the
per-cycle cost on every Phase 5 iteration and varies widely by hardware and pairing. Measure
it during Phase 2 and record it; it retroactively sharpens this entire estimate.
