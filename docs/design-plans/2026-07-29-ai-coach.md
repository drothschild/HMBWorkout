# AI Coach (Claude-Generated Workout Routines) Design

## Summary

Add an "AI Coach" chat screen that lets the user converse with Claude (via a hand-rolled Anthropic API client, since the official SDK doesn't run on Hermes/React Native) to draft new workout routines or edit existing ones. The system prompt is assembled from the user's stated goals, available equipment, current routines, and a capped slice of recent training history, so Claude's suggestions reflect what the user already does. Claude is constrained to respond with structured output matching a fixed `AiTurn` schema, guaranteeing every reply parses into a chat message plus an optional `RoutineDraft` — eliminating manual JSON-parsing/retry logic on the client.

The implementation is a single new vertical slice (`src/ai/`) sitting entirely in the app's imperative shell: no changes touch the Rill session engine, the sync bridge, or the vault markdown contract. Drafts are inert data until the user taps Accept, at which point they're mapped onto the same repository functions (`upsertExercise`/`upsertRoutine`) that manual routine editing already uses — so persistence, exercise-kind validation, and slug-based deduplication all reuse existing, tested code paths rather than introducing a parallel write path. Chat state itself is fully ephemeral and resets on every visit to the screen.

## Definition of Done

1. Settings gains three fields: Anthropic API key (secure storage), exercise-goals paragraph, and available-equipment description — persisted like the existing bridge settings.
2. A new AI chat screen talks to `claude-sonnet-5` using the user's key. Claude receives goals, equipment, existing routines, and recent workout history as context.
3. In chat, Claude proposes new routines or edits to an existing routine as structured draft cards; nothing is saved until the user taps Accept, which persists via the existing repository (free-form exercise names allowed, mapped to valid exercise kinds).
4. Chat is ephemeral (resets each visit). Session-flow engine, sync bridge, and markdown contract are untouched. Missing/invalid API key produces a clear prompt to fix Settings, not a crash.

## Acceptance Criteria

### ai-coach.AC1: Settings fields
- **ai-coach.AC1.1 Success:** Anthropic key, goals, and equipment save and survive app restart (reload from secure storage)
- **ai-coach.AC1.2 Success:** Pre-existing stored settings blobs (bridge URL/token only) load without error; new fields default to empty
- **ai-coach.AC1.3 Success:** Key input is masked (`secureTextEntry`); bridge settings remain unaffected by AI-field edits
- **ai-coach.AC1.4 Edge:** All three fields may be empty; app behaves normally

### ai-coach.AC2: Conversation with Claude
- **ai-coach.AC2.1 Success:** Sending a message yields an assistant reply rendered in the chat (via `claude-sonnet-5`, structured output)
- **ai-coach.AC2.2 Success:** System prompt contains goals, equipment, all existing routines, and recent working-set history
- **ai-coach.AC2.3 Success:** Edit mode's system prompt names the target routine and its `routineId`
- **ai-coach.AC2.4 Success:** Requests carry the settings key in `x-api-key`
- **ai-coach.AC2.5 Success:** Multi-turn conversations resend full history, including prior assistant drafts

### ai-coach.AC3: Draft + Accept persistence
- **ai-coach.AC3.1 Success:** A draft renders as a card; the database is untouched before Accept
- **ai-coach.AC3.2 Success:** Accepting a new-routine draft persists it via repository and navigates to the routine
- **ai-coach.AC3.3 Success:** Accepting a draft carrying `routineId` updates that routine in place
- **ai-coach.AC3.4 Success:** Free-form exercise titles create exercises with a valid `kind`; repeated titles converge on one exercise (slug dedupe)
- **ai-coach.AC3.5 Failure:** An invalid draft payload is rejected with no partial DB writes
- **ai-coach.AC3.6 Edge:** A newer draft replaces the pending one; only the latest is Accept-able

### ai-coach.AC4: Error handling
- **ai-coach.AC4.1 Success:** Missing key → chat shows "add key in Settings" state; no request is sent
- **ai-coach.AC4.2 Success:** 401 response → "API key rejected — check Settings" message
- **ai-coach.AC4.3 Failure:** Network failure → `AnthropicUnreachable`, inline error bubble with Retry; Retry re-sends the same turn
- **ai-coach.AC4.4 Failure:** Non-401 HTTP error → `AnthropicHttpError(status)`, error bubble, no crash
- **ai-coach.AC4.5 Failure:** Malformed/unparseable response body → typed parse error, no crash

### ai-coach.AC5: Ephemerality & isolation
- **ai-coach.AC5.1 Success:** Opening the chat screen resets conversation state
- **ai-coach.AC5.2 Success:** History context is capped (~5 working sets per exercise) so the prompt stays bounded
- **ai-coach.AC5.3 Success:** The chat flow performs no DB writes except through Accept
- **ai-coach.AC5.4 Success:** Accepting a draft never dispatches engine events or alters sessions/sync state

## Glossary

- **WatermelonDB**: The on-device SQLite-backed database that stores the app's routines, exercises, and sessions; the repository functions this design reuses (`upsertExercise`, `upsertRoutine`) are its write API.
- **LokiJS**: An in-memory JavaScript database used in place of WatermelonDB/SQLite on web and in Jest tests, so the same repository code can be exercised without a native runtime.
- **Zustand**: The state-management library used for the app's imperative-shell stores (e.g. the existing active-session store); this design adds a new ephemeral store (`aiChatStore.ts`) following the same factory/singleton pattern.
- **expo-router**: The file-based routing framework for the app (routes are files under `src/app/`); the new chat screen is added as a "Stack route" within it.
- **Rill / session engine**: The app's pure functional state machine that drives the live workout session (set logging, rest timers, phase transitions). This design explicitly does not touch it — the AI coach only writes routine data via the repository, the same way manual editing does.
- **Structured outputs**: An Anthropic API feature (`output_config.format` with a JSON schema) that constrains the model's response to conform to a given schema, so every assistant turn is guaranteed to parse into the app's `AiTurn` type without ad hoc validation or retries.
- **Hermes**: The JavaScript engine React Native uses on-device. Its `fetch` streaming support is unreliable, which is why this design uses a non-streaming request and a hand-rolled client instead of the official Anthropic SDK.
- **expo-secure-store**: The secure, encrypted on-device storage API used for sensitive values; the new Anthropic API key is persisted here, the same way existing bridge credentials are.
- **Superset (`supersetGroup`)**: A workout-domain concept where two or more exercises are performed back-to-back with no rest between them; a draft exercise can be tagged into a superset group.
- **Working set**: A single logged set of an exercise performed during a real session (as opposed to a routine's *target* sets/reps). The AI context includes recent working-set history so Claude's suggestions account for actual performance.
- **Slug / slug dedupe**: A normalized, identifier-safe form of a name (e.g. lowercased, hyphenated). Free-form exercise titles from Claude are slugified so that repeated titles (e.g. "Bench Press" typed twice) resolve to the same underlying exercise record instead of creating duplicates.
- **Presenter**: A read-model function (e.g. `routineListPresenter`, `routineDetailPresenter`) that derives display-ready data from engine/DB state for the UI or, here, for composing the AI's context — part of the app's functional-core/imperative-shell split.
- **Upsert**: A combined insert-or-update database operation; `upsertExercise`/`upsertRoutine` are the existing repository functions that create a record if it doesn't exist or update it in place if it does.
- **Vault markdown contract**: The shared markdown grammar (`src/interop/format.ts`) that syncs workout data to the user's Obsidian vault via a separate Mac-side bridge. Listed here only to note this design leaves it untouched.
- **`x-api-key` / `anthropic-version` headers**: The authentication and API-versioning headers required by Anthropic's Messages API; the design specifies these explicitly since the client is hand-rolled rather than SDK-based.

## Architecture

A new vertical slice, entirely in the imperative shell. The Rill session engine, sync queue, and vault markdown contract are untouched.

```
src/ai/
  anthropicClient.ts     — fetch wrapper for api.anthropic.com (mirrors src/sync/bridgeClient.ts)
  contextBuilder.ts      — assembles goals/equipment/routines/history into the system prompt
  draftSchema.ts         — JSON schema + TS types for {reply, draft?} structured responses
  acceptDraft.ts         — maps an accepted RoutineDraft onto repository upserts
src/state/
  aiChatStore.ts         — ephemeral Zustand store (messages, pending draft, status)
  settings.ts            — extended with anthropicKey, aiGoals, aiEquipment
src/app/
  ai-coach.tsx           — chat screen (Stack route)
```

**Model & transport.** `claude-sonnet-5` via a plain `fetch` POST to `https://api.anthropic.com/v1/messages` (headers `x-api-key`, `anthropic-version: 2023-06-01`), non-streaming, `max_tokens: 4096`. The official `@anthropic-ai/sdk` does not support React Native/Hermes, and Hermes fetch streaming is unreliable — a hand-rolled client is the researched recommendation and matches the codebase's bridge-client convention. Structured outputs (`output_config.format` with a JSON schema) guarantee every assistant turn parses as `AiTurn`.

**Data flow.** Chat screen → `aiChatStore.send(text)` → (first turn) `contextBuilder.buildSystem(db, mode)` → `anthropicClient.chat({system, messages})` → parsed `{reply, draft?}` → store update → screen renders reply bubble plus a draft card when present → Accept → `acceptDraft(db, draft)` → existing `upsertExercise`/`upsertRoutine` → navigate to `/routine/[id]`.

**Entry points.** "AI Coach" button on the routines tab (create mode) and on the routine detail screen (edit mode). Edit mode includes the target routine in context with an instruction to return drafts as revisions preserving its `routineId`.

**Contracts.**

```typescript
// draftSchema.ts — the shape Claude must return (enforced via structured outputs)
interface AiTurn { reply: string; draft?: RoutineDraft }
interface RoutineDraft {
  routineId?: string;          // present only when editing an existing routine
  name: string;
  notes?: string;
  exercises: DraftExercise[];
}
interface DraftExercise {
  title: string;               // free-form; may name a brand-new exercise
  kind: 'strength' | 'cardio' | 'stretch';
  supersetGroup?: string;
  warmupSets?: number;
  targetSets?: number;
  targetReps?: number;
  targetDurationSeconds?: number;
  restSeconds?: number;
  notes?: string;
}

// anthropicClient.ts
function createAnthropicClient(
  config: { apiKey: string },
  fetchFn?: typeof fetch
): {
  chat(request: {
    system: string;
    messages: { role: 'user' | 'assistant'; content: string }[];
  }): Promise<AiTurn>;
};
class AnthropicUnreachable extends Error {}
class AnthropicHttpError extends Error { status: number }  // 401 surfaced distinctly in UI

// settings.ts — extended record (existing fields unchanged)
interface AppSettings {
  baseUrl: string;
  token: string;
  anthropicKey: string;
  aiGoals: string;
  aiEquipment: string;
}
```

Assistant turns are re-sent verbatim (the raw JSON string) as conversation history so Claude sees its own prior drafts. Chat state is ephemeral: `reset()` runs on screen mount; no new DB tables.

## Existing Patterns

Codebase investigation (2026-07-29) found the following patterns, all of which this design follows:

- **Settings**: module-level cache + injected secure-store backend (`src/state/settings.ts`), hydrated at boot in `src/app/_layout.tsx` via `injectSettingsStorage`/`loadSettings`. New fields extend the same JSON blob under the existing storage key; `getSettings()`/`setSettings()` API unchanged. Settings UI follows the useState → TextInput → `setSettings` pattern of `src/app/(tabs)/settings.tsx`.
- **HTTP client**: factory + injectable fetch + typed error classes, per `src/sync/bridgeClient.ts` (`BridgeUnreachable`/`BridgeHttpError` → `AnthropicUnreachable`/`AnthropicHttpError`).
- **Persistence**: `upsertExercise(db, exerciseId, title, kind)` (keyed by slug id, `src/db/repository.ts`) and `upsertRoutine(db, routineId, name, RoutineExerciseEntry[], {notes?})` (single transaction; reconciles routine_exercises in place so surviving rows keep their ids and attached set history, `src/db/repository.ts`). No new write paths.
- **Read models**: `routineListPresenter`/`routineDetailPresenter` (`src/state/`) and `getExerciseWorkingSetHistory` (`src/db/repository.ts:190`) feed the AI context; no new queries beyond composition.
- **Store**: factory + lazy singleton Zustand pattern per `createActiveSessionStore` (`src/state/activeSession.ts`), with injectable dependencies for node-Jest testability.
- **Screens**: expo-router Stack route, ThemedView/ThemedText, Spacing constants, SafeAreaView — per `src/app/routine/[id].tsx` and `src/app/(tabs)/settings.tsx`.

Divergence: none. The AI slice introduces one new directory (`src/ai/`), consistent with the per-domain layout (`src/sync/`, `src/health/`).

## Additional Considerations

**Edit history preservation:** `upsertRoutine` reconciles `routine_exercises` in place (PR #12): rows for exercises that survive an edit keep their ids, so prior sessions' set references — and the working-set history fed into the AI context — survive routine edits, whether made manually, by vault re-import, or via an accepted AI draft. Only exercises actually removed from a routine detach their logged sets.

**Prompt size:** history is capped (~5 working sets per exercise) to keep the system prompt to a few thousand tokens. If users accumulate many routines, the cap keeps cost roughly constant per conversation.

**Key security:** the key lives in expo-secure-store and is only ever sent to `api.anthropic.com` over HTTPS. It is never logged and never included in vault sync payloads.

**No engine involvement:** the chat never dispatches engine events or touches session flow; it only writes routines via the repository, same as manual editing.
